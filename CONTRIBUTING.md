# Contributing: module conventions

Feature modules are built in parallel, for example students, batches, attendance, fees, exams and LMS. Follow these rules so modules stay independent and merge without conflicts. **A new module should not need edits to any shared file.** If you think it does, raise it with the platform owners instead of patching core files in your feature branch.

Read [ARCHITECTURE.md](ARCHITECTURE.md) first. The reference implementations to copy are:

- Backend: `backend/src/modules/branches/`
- Frontend: `app/src/modules/branches/`

## Backend module

### 1. Scaffold

```bash
npm run make:module -w backend -- students
npm run make:migration -w backend -- students add-guardian-columns   # later migrations
```

This creates:

```
backend/src/modules/students/
  index.ts                 # export default defineModule({ name, models, associate?, routes, permissions, jobs?, onReady? })
  students.model.ts        # Sequelize v6 TS model: static initModel(sequelize) + registerTenantModel(Model)
  students.routes.ts       # export function studentRoutes(api: Router) { ... api.use('/students', r) }
  students.service.ts      # add yourself: business logic (keep routes thin)
  migrations/YYYYMMDDHHMMSS-create-students.ts
  seeders/                 # optional: demo data, same timestamp naming
```

The module loader picks up the folder automatically, and the migrator picks up `migrations/` and `seeders/`.

### 2. Naming and database rules

| Thing                                            | Convention                                                                                                                                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Module folder, URL prefix, permission module key | kebab-case, the same everywhere: `fee-receipts` → `/api/fee-receipts`, `fee-receipts.view`                                                                                   |
| Tables and columns                               | snake_case plural tables (`fee_receipts`). Models use camelCase attributes (`underscored: true` is global)                                                                   |
| Migration file                                   | `YYYYMMDDHHMMSS-verb-object.ts`, generated by `make:migration`, exporting `up`/`down` typed as `Migration`                                                                   |
| Primary key                                      | `id()` helper (INT UNSIGNED auto-increment)                                                                                                                                  |
| Timestamps                                       | `timestamps()` helper                                                                                                                                                        |
| Tenant columns                                   | **Every tenant-owned table uses `...tenantColumns()`**, or `tenantColumns({ branch: 'required' \| 'optional' })` for branch data. Add indexes that start with `institute_id` |
| Foreign keys                                     | `fk('table')` helper. Cross-module FKs may point only at tables of modules that already exist (core, or earlier timestamps)                                                  |
| Migration history                                | Never edit a merged migration. Add a new one                                                                                                                                 |

### 3. Tenancy

- **Register the model.** Call `registerTenantModel(Model)` in `initModel`. Any query without `instituteId` then throws, as a safety net.
- **Use the repository.** Do all tenant data access through `new TenantRepository(Model, { entity: 'Student', branchScoped: true })`.
  - Use `findAll`, `findById`, `findOne`, `findAndCountAll`, `count`, `create`, `update`, `destroy`, `scope(where)` and `assertBranchAllowed(branchId)`.
- **Institute-wide rows.** For branch data that may also be institute-wide (`branch_id` NULL, e.g. files, notices), pass `instituteWideRows: true`. Every user of the institute can then read NULL-branch rows, but only institute-level users can change them (`repo.assertRowWritable(row)` is applied by `update`/`destroy`). Rows created by branch-restricted users always get a branch: their active or only branch, otherwise 400 `BRANCH_REQUIRED`.
- **Tenant ids come only from context.** Read the institute and branch from `requireTenantContext()` or `getContext()`. **Never** take `instituteId` from the body, query or params.
  - The `branchId` in a body is allowed, but must be checked with `repo.assertBranchAllowed()`.
- **Bypasses.** `{ tenantBypass: true }` is only for super-admin platform code or system jobs, and must come with a comment.
- **Not-found behaviour.** A record from another institute must result in **404**.

### 4. Permissions (RBAC)

Declare permissions in `index.ts`. They are synced on boot, and system-role grants are applied:

```ts
permissions: [{
  module: 'students', label: 'Students',
  actions: ['view', 'create', 'edit', 'delete', 'export'],
  grants: { 'branch-admin': 'all', teacher: ['view'], accountant: ['view', 'export'] },
}],
```

- Protect every route with `authenticate`, then `requirePermission('students', 'create')`. Institute admin implicitly holds all permissions.
- If the module is a sellable plan feature, also add `requireModule('students')`, and put the key in plan `enabledModules`.
- Actions are limited to `view | create | edit | delete | approve | export | publish | configure`.
- Self-service data, such as a student viewing their own results, still needs a permission check plus an ownership check in the service. Ownership comes from `getContext().userId`.

### 4b. Mounting routes and public routes

- Mount every router under your module's prefix: `api.use('/students', r)`. Apply `authenticate` **per router** (`r.use(authenticate)`) or per route.
- **Never** call `api.use(middleware)` or `api.use('/', router)`. Router-level middleware at the root runs for every module registered after yours (modules load alphabetically), so `authenticate` there would return 401 for their public routes. `createApp` refuses to boot if a module does this (`test/routing.test.ts`).
- `/admin/*` is reserved for super-admin platform routes. Those routers use `authenticate, requireSuperAdmin`, so don't put tenant or public routes there.
- **Public (unauthenticated) routes** go on a separate router or an individual route without `authenticate`, under your prefix. Give them their own rate limit if they are abuse-prone, and validate input as usual:

```ts
export function admissionRoutes(api: Router) {
  const pub = Router(); // public: e.g. online enquiry form
  pub.post('/enquiries', authRateLimit, async (req, res) => {
    /* ... */
  });
  api.use('/admissions/public', pub);

  const r = Router();
  r.use(authenticate);
  r.get('/', requirePermission('admissions', 'view'), async (_req, res) => {
    /* ... */
  });
  api.use('/admissions', r);
}
```

Register the public router before the authenticated one when they share a prefix, as above. Public handlers have no tenant context, so resolve the institute explicitly (e.g. from a signed token or a public institute code) and pass `{ tenantBypass: true }` only with a comment explaining why.

### 5. Request handling

- Validate input with zod using `parse(schema, req.body | req.query | req.params)`. Use `idParam` and the pagination helpers from `shared/utilities`.
- Throw the helpers from `shared/errors` (`NotFound`, `Forbidden`, `Conflict`, `BadRequest`, `LimitExceeded`). Never `res.status(500)` by hand. Express 5 forwards async errors on its own.
- Error shape is always `{ error: { code, message, details? } }`. List endpoints return `{ items, total, page, pageSize }`.
- Call `audit({ action: 'students.create', entityType: 'Student', entityId, after })` for every create, update, delete, approve or publish of business data. Include `before` for updates and deletes.
- Check plan limits with `assertWithinLimit(instituteId, 'maxStudents', currentCount)` before creating limited entities.

### 6. Use platform services; never call vendors directly

- **Files**: `saveUploadedFile()` and `signedUrlFor()`. Store `file_id` FKs to `files`, never paths or public URLs.
- **AI**: `aiChat({ feature: '<module>.<feature>', messages })`. Don't read AI settings or keys yourself.
- **Messaging, payments, streaming, biometric**: use the adapters under `infrastructure/`. Don't import vendor SDKs in modules.
- **Long or retryable work**:
  - Queue it with `enqueueJob('<module>.<job>', payload)`.
  - Register the handler in the module's `jobs` map.
  - Handlers run with the job's tenant context.

### 7. Tests (required)

Add `backend/test/<module>.test.ts` using the helpers in `test/helpers.ts`: `getApp`, `login`, `USERS` and `bearer`. Each module must cover at least:

1. Happy-path CRUD for an authorised role.
2. **403** for a role without the permission.
3. **Tenant isolation**: Apex cannot read or update Zenith data (404), and a client-supplied `instituteId` is ignored. See `test/tenancy.test.ts`.

Set a per-checkout `TEST_DB_NAME` in `backend/.env` (e.g. `erp_coaching_test_<module>`) so parallel sessions don't share a database. Tests run against the real MySQL test database, which is dropped, migrated and seeded once per run. Commands:

- `npm test -w backend`
- `npm run typecheck`
- `npm run lint`

## Frontend module

```
app/src/modules/students/
  module.ts            # export default defineAppModule({ id, routes, menu })
  api.ts               # typed wrappers around core/api (api.get/post/patch/delete/upload)
  StudentsPage.vue     # pages; sub-components in components/
```

```ts
export default defineAppModule({
  id: 'students',
  routes: [
    {
      path: '/students',
      name: 'students',
      component: () => import('./StudentsPage.vue'),
      meta: { permission: 'students.view' },
    },
  ],
  menu: [
    {
      title: 'Students',
      path: '/students',
      icon: peopleOutline,
      permission: 'students.view',
      planModule: 'students',
      order: 30,
    },
  ],
});
```

- **Discovery.** Modules are auto-discovered with `import.meta.glob`, so don't edit `router/` or `App.vue`.
- **Routes.**
  - Route paths are prefixed with the module id.
  - Always lazy-load pages.
  - Set `meta.permission` (or `meta.superAdmin` for platform screens).
- **Pages.** Wrap every page in `<AppPage title="…">`, which provides the header, menu button and pull-to-refresh.
- **UI.** Use Ionic components so the app works on web, Android and iOS.
- **Permissions.** Hide actions with `v-can="'students.create'"`, or use `auth.can('students.create')` in script.
  - UI checks are a convenience. **The backend is the authority.**
- **API calls.**
  - Go through `core/api.ts` only, never raw `fetch` or axios. It handles tokens, refresh and `X-Branch-Id`.
  - Show errors with `errorMessage(e)` and `toast`.
- **Branding.** Use Ionic colour variables (`var(--ion-color-primary)`) and never hard-code brand colours.
- **Native APIs.** Use Capacitor plugins and guard them with `Capacitor.isNativePlatform()` when behaviour differs.
- **Shared types.** Request and response DTOs used by both sides go in `packages/shared/src/<module>.ts`, exported from its `index.ts`. That one-line export is the only shared edit expected.

## Git and PRs

- One module per branch and PR. Keep the PR focused on `backend/src/modules/<name>`, `app/src/modules/<name>`, its tests, and `packages/shared/src/<name>.ts`.
- `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` must pass.
- Never commit `.env`, `backend/storage/` or secrets.
